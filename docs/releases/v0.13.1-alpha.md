# v0.13.1-alpha - Honest OpenCLI runtime errors

Omnireach no longer reports every OpenCLI failure as an unconfigured source.

A real Douyin search briefly failed with `1 个源未配置`, then succeeded repeatedly with
the same installation, directory, Chrome profile, and query. The Douyin adapter was healthy;
the shared OpenCLI bridge had collapsed all subprocess and response-contract failures into
`AdapterUnavailable`, and the TTY renderer hid the original detail.

## What Changed

- Missing `opencli` still produces an `unavailable` source error and setup guidance.
- A nonzero OpenCLI exit now produces a `failed` source error with stderr/stdout detail.
- Malformed JSON and invalid result shapes now produce visible `failed` errors.
- TTY output prints the source and real OpenCLI failure instead of the generic
  `源未配置` summary.
- Silent background, ephemeral, close-after-use Chrome behavior is unchanged.

No new runtime dependency was added.

## Verification

- Unit coverage for nonzero exits, malformed JSON, invalid shapes, and missing binaries.
- Dispatcher coverage proves OpenCLI command errors are classified as `failed`.
- TTY coverage reproduces the reported Douyin symptom and verifies the real detail is shown.
- Real Douyin search returns live results with `errors=[]`.

## Toward Removing OpenCLI

The next architectural step is an internal browser-transport interface, followed by an
Omnireach-owned read-only Chrome extension and Python bridge. OpenCLI can then remain a
fallback while sources migrate individually. Directly decrypting Chrome cookies or attaching
CDP to an already-running normal profile does not reliably replace the authenticated browser
component.

uv tool install --force 'omnireach==0.13.1a0'
