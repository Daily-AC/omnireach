# Lessons Learned: v0.3 → v0.5 cycle

**Date**: 2026-05-26
**Context**: After v0.5 ship, a real user deploying fresh found that `--on twitter` crashed with `'list' object has no attribute 'get'`. Their agent traced the bug; v0.5.2 hotfix backported the fix. This doc captures what the cycle taught us so v0.6+ doesn't repeat.

## 1. Heavy-tier subprocess adapters MUST be e2e smoke-tested with the real binary before ship

**Symptom**: twitter and xiaohongshu adapters were broken from v0.3 ship to v0.5.1 (~3 milestones, 4 releases). All mock tests passed. Real user hit it within 10 minutes of installing.

**Root cause**: The mock fixtures were hand-written based on imagined opencli output shape (`{"results": [...]}` dict). Real opencli `-f json` returns a top-level JSON array. Contract drift between the mock and the real binary went undetected because no test invocation ever crossed into the actual `opencli` process.

**Rule going forward**: For any adapter that shells out to an external binary (heavy tier, plus reddit's rdt-cli, github's gh, youtube's yt-dlp), the release checklist MUST include one manual run that calls the real binary at least once. Capture the real output as a fixture. Don't hand-write fixtures.

**How to apply**:
- `scripts/smoke_<version>.sh` should grow a per-binary section: `if shutil.which(binary): run a real query and assert non-empty results`
- Block release if smoke flags any source as broken (`omnireach setup <X>` should fix and re-run smoke)
- Treat mock-only test coverage as a yellow flag, not a green one

## 2. CLI flag contracts drift across upstream binary versions

**Symptom**: v0.3 adapter called `opencli twitter search --json`. opencli v1.7.22 (current as of 2026-05-26) only accepts `-f, --format <fmt>` with `json` as a choice — `--json` was never a flag, or was removed. Adapter crashes silently because subprocess fails non-zero and gets caught as `AdapterUnavailable` (the user sees "opencli not installed" or similar, masking the real issue).

**Rule going forward**: For each upstream binary dependency, the release checklist MUST run `<binary> <subcmd> --help` and diff against the adapter's argv. Catch flag drift before it ships.

**How to apply**:
- A `scripts/verify-adapter-contracts.sh` that for each adapter loads its argv shape, runs `<binary> <subcmd> --help`, and prints a diff/warning for any unknown flag
- Document upstream binary version pins in sources.yml comments (e.g. `# opencli >= 1.7.0; --format flag introduced in 1.5`)

## 3. Default `--timeout` cannot be one-size-fits-all

**Symptom**: User had to manually pass `--timeout 45` to make twitter search work. Default 15s killed OpenCLI before it finished waking Chrome session.

**Rule going forward**: Either:
- (a) raise global default to a value that fits heavy tier (e.g. 30s), accepting that lightweight sources will fanout slower than needed
- (b) implement per-source timeout overrides in sources.yml (e.g. `timeout_seconds: 30` per source)

v0.5.2 chose (a) — global default 30s — for simplicity. v0.6+ should consider (b) so HN doesn't pay opencli's latency cost.

**How to apply**:
- When adding a new source, look at its expected p50/p95 latency and set sources.yml `timeout_seconds` explicitly
- Dispatcher reads per-source timeout, falls back to CLI `--timeout` flag, falls back to global default

## 4. Default mode is too noisy when sources aren't all set up

**Symptom**: User ran `omnireach search "claude code"` (default mode = auto fanout to all default_in_auto sources). Output had 5 ✗ red error rows from sources without binaries/keys. User's agent had to manually pivot to `--mode quick` to get clean output.

**Rule going forward**: Errors from sources that are **not configured** (binary missing, env var unset) should NOT print as red ✗ rows in TTY output. They should be silently skipped (dispatcher still tracks them in JSON `errors[]` for debugging), and `omnireach doctor` is where users see "you have unconfigured sources".

**How to apply**:
- Classify dispatcher errors: `unavailable` (config issue — silent) vs `failed` (actually broke at runtime — print red)
- TTY renderer only prints red rows for runtime failures
- JSON output keeps everything for downstream pipes
- Add a footer line "N source(s) not configured; run `omnireach doctor`" instead of inline noise

This is v0.6 UX work, not a hotfix.

## 5. Plugin manifest is cross-CLI compatible — marketing surface we didn't know about

**Surprise**: User installed omnireach via Antigravity's `agy plugin install .claude-plugin/`, and the SKILL.md got picked up natively. agy and Claude Code share the plugin manifest schema.

**Going forward**:
- v1.0 README should explicitly list compatible CLIs: Claude Code, Antigravity, (possibly OpenClaw, Cursor — verify)
- Skill description should be tested in non-Claude-Code agents too — the wording might activate differently

## 6. Users' agents auto-fix upstream bugs locally but the fix doesn't flow back

**Observation**: User's agent diagnosed the v0.5.1 opencli bugs, edited `omnireach/adapters/{twitter,xiaohongshu}.py` in a local clone, ran `uv tool install --force /local/path`, and verified the fix works — all autonomously. The fix lived in their `~/projects/games/omnireach` and never made it to upstream. The next user installing v0.5.1 would have hit the same crash.

**Going forward** (v1.0+ wishlist, not v0.6):
- A `omnireach diagnose --autopr` command that:
  1. Compares local repo head to remote upstream
  2. Computes a diff
  3. Opens a PR (after user confirmation) attributing the patch
- Or: tell users explicitly in setup wizard "if your agent autonomously edits omnireach source to fix a bug, please open a PR — see CONTRIBUTING.md"

The first option is highly novel and aligns with the project's "give Agent users superpowers" thesis. Worth a v1.x design pass.

## 7. Mock-passing isn't deployment-passing

**Meta-lesson**: All 159 tests in v0.5.1 pass. Yet the deployment was broken for two whole sources. The lesson isn't "more tests" — it's that **test taxonomy matters**. We had unit tests but no contract tests against the real upstream, no e2e tests against the real CLI surface.

Future release checklist:
- [ ] Unit tests pass (`uv run pytest -x`)
- [ ] Smoke script runs against real binaries (where present)
- [ ] One manual invocation of each ready/heavy source with real query
- [ ] Doctor shows expected status for each source
- [ ] `omnireach check-update` works against real GitHub Releases API

The first one is automation. The other four are 5 minutes of manual work but catch the drift class of bug.
