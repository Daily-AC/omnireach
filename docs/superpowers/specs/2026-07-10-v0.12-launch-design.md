# v0.12 Evidence-Led Launch Design

Date: 2026-07-10
Status: Approved for implementation and external publication

## Context

Omnireach has six GitHub stars, but its last 14 days show 51 unique cloners and 27
unique repository visitors. The repository is generating trials without converting those
trials into durable interest. The latest public release is still `v0.11.0-alpha`, while
the dependency-free MCP search and fetch fast path is already merged to `main`.

Generic "AI agent CLI" launches perform poorly in a crowded category. Successful launches
make one painful workflow concrete and show measured evidence. Omnireach has two credible,
complementary wedges:

- ordinary read-only web work should not require launching browser automation;
- login-walled Chinese sources can reuse the user's existing Chrome session when HTTP is
  insufficient.

The launch must preserve both. A broad Playwright-replacement claim would be inaccurate,
because omnireach does not click, submit forms, upload files, or perform visual assertions.

## Goal

Turn the merged MCP fast path into a versioned, reproducible launch event that gives agent
developers a concrete reason to try, discuss, and star omnireach.

## Positioning

The global launch message is:

> Search and fetch before you automate a browser. Omnireach gives agents two read-only MCP
> tools; ordinary pages use HTTP, while supported login-walled sources silently reuse the
> user's Chrome session only when required.

The Chinese launch message leads with WeChat and Xiaohongshu access, then explains the same
two-path architecture. The existing README headline remains WeChat-first because it is the
project's strongest product-level differentiation. A compact fast-path proof is added near
the top instead of replacing that identity.

Every launch post must disclose that it is from the author. Posts ask for technical feedback
and real use cases, not reciprocal stars. No bought stars, bot accounts, vote rings, private
message spam, or claims that cannot be reproduced are permitted.

## Release Package

Publish `v0.12.0-alpha` after the implementation branch is reviewed and merged. The release
contains four public artifacts:

1. A deterministic benchmark harness for comparing omnireach's MCP fetch path with cold and
   warm headless Chrome navigation through Playwright.
2. Raw benchmark JSON containing every sample, environment metadata, exact URL, and command.
3. A short benchmark report that states the scope and limitations of the comparison.
4. A terminal demo showing an ordinary fetch through MCP without opening a visible Chrome
   window, alongside a real logged-in Xiaohongshu search using the existing silent bridge.

The comparison is explicitly a read-only page retrieval benchmark. It must not imply that a
single HTTP extractor replaces browser automation for interactive tasks. Playwright is run
headless in the benchmark so the measured claim concerns startup and navigation cost, not a
claim that Playwright always opens a visible tab.

## Benchmark Contract

Add `scripts/benchmark_read_path.py`. It uses the real `omnireach mcp` stdio server and the
real Playwright Python package with the installed Chrome channel. It measures:

- cold omnireach MCP startup plus one `omnireach_fetch` call;
- warm omnireach MCP calls through one persistent server;
- cold headless Chrome startup, navigation, and body-text extraction;
- warm headless Chrome navigation through one persistent browser.

The default target is a stable, public HTML document. Each path runs five measured samples
after one untimed warm-up when applicable. A run fails if any response is empty, reports an
MCP tool error, returns a non-success navigation status, or produces fewer than 500 text
characters. Results include Python, omnireach, Playwright, Chrome, OS, architecture, UTC
timestamp, target URL, and raw millisecond samples. The report uses medians and retains raw
values so readers can recompute them.

Tests cover sample validation, median calculation, result serialization, and benchmark
report rendering without invoking a real browser. The real release verification runs the
full harness against the network and system Chrome.

## Documentation And Assets

Update both READMEs with:

- a near-top "MCP before Playwright" proof block linking to the raw benchmark;
- exact language about ordinary HTTP pages versus login-backed hidden ephemeral tabs;
- an explicit boundary that keeps Playwright for interaction and visual work;
- the new version's installation and release references where versioned text appears.

Add a release note file and channel-specific launch copy under `docs/launch/`. The copy file
is public and reviewable. It contains final titles, bodies, source disclosure, asset links,
and a small response bank for predictable technical questions about Chrome, login state,
anti-bot behavior, and Playwright scope.

The fast-path terminal demo is generated from a checked-in VHS tape. It must show commands
that were run successfully during release verification; no fabricated benchmark output is
typed into the recording.

## Distribution

Distribution happens only after the release URL and benchmark links are live:

1. Update the two existing awesome-list pull requests with the material new release and
   benchmark; do not post empty "bump" comments.
2. Submit a factual Show HN launch with the benchmark, architecture, and limitations.
3. Publish an English X thread with the side-by-side result and demo asset.
4. Submit tailored, rule-compliant posts to relevant Reddit communities. Check each
   community's current self-promotion rules immediately before posting.
5. Publish Chinese versions to V2EX and Xiaohongshu when the logged-in accounts permit it.

The same copy is not pasted unchanged across communities. Each post answers that community's
likely question and links directly to the repository or release. If a platform requires
CAPTCHA, 2FA, or a destructive account change, stop at the prompt instead of bypassing it.

## Measurement

Record a pre-launch snapshot of stars, forks, unique visitors, unique cloners, referrers,
and release downloads. Record the same fields 24 hours and seven days after launch. The
primary conversion metric is new stars per unique repository visitor. Secondary signals are
substantive comments, issues, external references, and successful installs. Raw star count
alone is not treated as evidence of product fit.

## Non-Goals

- Replace Playwright for browser interaction or visual testing.
- Build a hosted analytics service or add tracking code to the package.
- Redesign the entire README or project identity.
- Promise that every anti-bot system can be bypassed.
- Automate voting, reciprocal starring, or unsolicited direct outreach.
- Publish benchmark numbers that were not produced by the checked-in harness.

## Completion Criteria

- `v0.12.0-alpha` is merged, tagged, released, and installable from the documented paths.
- The full unit suite, package build, install smoke test, and real benchmark all pass.
- Raw benchmark data and the generated report agree.
- The ordinary fetch demo opens no visible Chrome window; the Xiaohongshu run returns real
  logged-in results without changing the visible Chrome window count.
- Existing awesome-list pull requests receive one substantive update.
- Rule-compliant launch posts are live on every authorized platform where the current account
  is already authenticated and no human verification blocks publication.
- Baseline metrics are saved for later 24-hour and seven-day comparison.
